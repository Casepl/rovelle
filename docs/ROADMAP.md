# Rovelle: дорожная карта

Rovelle — экспериментальная платформа инкрементальной сборки и доставки
программ, конфигурации и моделей. Первый практический сценарий — SSR-приложения:
от хранения одного файла до согласованного релиза на нескольких экземплярах.

Общая линия канала:

> **От улья до автономного производства: один инженер строит Physical AI с нуля**

Рабочее название первого сезона:

> **В одиночку пишу платформу доставки, которую в бигтехе строят командами**

Первый сезон посвящён deploy-платформе. Инкрементальная сборка, независимые
Next.js zones, компонентный runtime и визуальные тесты развиваются следующими
сезонами.

## Дальняя цель

Rovelle должна стать нижним слоем для доставки кода, конфигурации и моделей.
Следующий самостоятельный продукт — журнал и аналитическое хранилище событий
производства. На них можно построить цифровую модель процессов, симуляцию и
контур управления AI-агентов.

Два первых физических сценария:

- робот-помощник пчеловода: Unity-симулятор, ROS 2, датчики и исполнительные
  механизмы;
- производство медовухи: партии, рецептуры, оборудование, телеметрия и полная
  история технологического процесса.

Это отдельные приложения с общей инфраструктурой доставки, идентификации,
desired state и событий. Автономность развивается по ступеням: наблюдение,
объяснение, рекомендация, симуляция, подтверждение человеком и только затем
ограниченное автоматическое управление.

## Принципы

1. Blob и опубликованная ревизия неизменяемы.
2. Физический адрес содержимого определяется его SHA-256.
3. Application revision фиксирует точные ревизии всех модулей.
4. Один SSR-запрос использует одну application revision от начала до конца.
5. HTML загружает browser assets той же ревизии, на которой выполнен SSR.
6. Экземпляр продолжает обслуживать последнюю активную ревизию без control plane.
7. Новый релиз сначала подготавливается, затем активируется.
8. Rollback использует опубликованную ревизию и не запускает сборку.
9. Падение SSR-процесса не завершает gateway или агент экземпляра.
10. Повтор команды или события безопасен.

## Границы v0.1.0

В первую версию входят:

- локальный control plane;
- content-addressed storage;
- три локальных экземпляра приложения;
- pull-доставка blobs;
- prepare/activate rollout;
- gateway с выбором application revision;
- прогрев и drain SSR-процессов;
- согласованный SSR и browser assets;
- восстановление control plane из журнала;
- rollback без пересборки;
- адаптер целого Next.js standalone build.

В первую версию не входят Kubernetes, Kafka как обязательная зависимость,
удалённые build workers, multi-tenant авторизация, canary, web-интерфейс,
запуск недоверенного кода и визуальное тестирование.

## Компоненты

| Компонент | Язык | Ответственность |
| --- | --- | --- |
| `rovelle-store` | C | CAS, SHA-256, проверка и атомарная запись blobs |
| `rovelle-control-plane` | Go | manifests, desired state, leases и rollout |
| `rovelle-agent` | Rust | доставка, локальный кеш и reconciliation |
| `rovelle-build` | Rust | граф задач и инкрементальный кеш |
| `rovelle-supervisor` | C++ | SSR-процессы, IPC, таймауты и drain |
| `rovelle-sdk` | TypeScript | framework adapters, SSR и browser runtime |
| `rovelle-lab` | Python | локальный кластер и fault injection |

Компоненты взаимодействуют через HTTP, SSE и версионированные форматы данных.
Kafka позднее может стать реализацией интерфейса `EventLog`, но не требуется для
локального запуска или корректности базового rollout.

## Сезон 1: deploy-платформа

Каждый стрим заканчивается работающей демонстрацией и зафиксированным
архитектурным решением.

### 1. У файла появляется идентификатор

**Язык:** C.

Реализовать потоковое вычисление SHA-256 и команду `rovelle hash <file>`.
Сравнить результат с системной утилитой на текстовом, бинарном и пустом файлах.

Результат: одинаковое содержимое всегда получает один 64-символьный
идентификатор независимо от имени файла.

### 2. Складываем содержимое по хешу

**Язык:** C.

Добавить команды `blob put` и `blob get`, размещение содержимого по хешу и
атомарную запись через временный файл.

Результат: повторная загрузка одинакового содержимого не создаёт новую копию,
а частично записанный blob никогда не становится доступен читателю.

### 3. Релиз — это manifest, а не архив

**Языки:** C и описание протокола.

Добавить manifest артефакта, проверку всех ссылок на blobs и неизменяемый
идентификатор ревизии.

Результат: каталог релиза полностью восстанавливается из manifest и CAS.

### 4. Пишем свой control plane без Kubernetes

**Язык:** Go.

Создать приложения, окружения, application revisions и desired state. Все
изменения записывать в локальный append-only журнал.

Результат: после перезапуска control plane состояние восстанавливается.

### 5. Поды сами забирают релиз

**Язык:** Rust.

Реализовать агента, который получает desired state, скачивает отсутствующие
blobs, проверяет хеши и собирает каталог ревизии.

Результат: потеря локального кеша исправляется reconciliation loop.

### 6. Новый релиз без перезапуска экземпляра

**Языки:** Go и Rust.

Реализовать состояния `PREPARING`, `READY`, `ACTIVATING` и атомарное
переключение `current`.

Результат: три экземпляра переходят на новую ревизию, а уже начатый запрос
завершается на старой.

### 7. Клиент не должен смешивать две версии

**Компоненты:** gateway и CDN-модель.

Gateway выбирает application revision и передаёт её через
`X-Rovelle-Revision`. HTML содержит ревизионные URL browser assets. Affinity
cookie резервируется для canary и закрепления пользователя за ревизией.

Результат: SSR и гидратация всегда используют совместимые артефакты.

### 8. Деплоим Next.js как обычный артефакт

**Язык:** TypeScript.

Добавить адаптер для `output: "standalone"`, `deploymentId`, `.next/static`,
health check и graceful shutdown.

Результат: Rovelle публикует, прогревает, переключает и откатывает целый
Next.js build.

### 9. Падение SSR не должно уронить приложение

**Язык:** C++.

Реализовать supervisor: отдельные процессы, IPC, таймаут, ограничение
параллелизма, health check и graceful drain.

Результат: аварийное завершение SSR-процесса даёт fallback и не завершает
gateway или агент.

### 10. Rollback быстрее новой сборки

**Компоненты:** control plane, agent и supervisor.

Добавить хранение последних успешных ревизий, прогрев старого process pool и
rollout на существующий snapshot.

Результат: rollback не скачивает имеющиеся blobs и не запускает сборку.

### 11. Ломаем собственную платформу

**Язык:** Python.

Создать `rovelle-lab`: запуск локального кластера, остановка агента, потеря
связи, повреждение временного blob и падение control plane.

Результат: автоматические сценарии подтверждают основные инварианты системы.

### 12. Полная демонстрация v0.1.0

Изменить Next.js-приложение, опубликовать новую ревизию, доставить только новые
blobs на три экземпляра, переключить трафик, уронить SSR-процесс и выполнить
rollback.

Результат: воспроизводимая команда `rovelle-lab demo` и измерения времени,
переданных байтов, ошибок SSR и скорости rollback.

## Первая задача

Первая самостоятельная задача — `RVL-001: content-addressed blob`.

Нужно добавить:

```text
include/rovelle/blob.h
src/blob.c
```

И расширить:

```text
cli/main.c
CMakeLists.txt
README.md
```

Минимальный интерфейс библиотеки:

```c
rovelle_status_t rovelle_blob_put(
    const char *store_path,
    const char *source_path,
    char out_hash[65]
);

rovelle_status_t rovelle_blob_get(
    const char *store_path,
    const char *hash,
    const char *destination_path
);
```

Команды:

```text
rovelle blob put <store> <file>
rovelle blob get <store> <sha256> <destination>
```

Задача готова, когда одинаковые файлы получают одинаковый хеш, повторный
`put` безопасен, повреждённый blob обнаруживается, а итоговый файл никогда не
появляется в store частично записанным.
