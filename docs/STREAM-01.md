# Стрим 1: у файла появляется идентификатор

## Карточка стрима

**Основной заголовок:**

> 13 лет не писал на C. Начинаю инфраструктуру для автономного производства

**Подзаголовок:**

> Пишем первый кирпич Rovelle: идентификатор содержимого файла

**Обещание зрителю:** к концу стрима команда `rovelle hash <file>` читает файл
частями и печатает его SHA-256. Одинаковое содержимое получает одинаковый
идентификатор, даже если файлы называются по-разному.

**Продолжительность:** 90 минут основной работы и до 30 минут на проверку,
вопросы и разбор проблем.

## Зачем это всей системе

Rovelle должна доставлять на экземпляры только изменившиеся части релиза. Для
этого содержимое сначала получает адрес, вычисленный из него самого:

```text
файл -> SHA-256 -> blob -> manifest -> revision -> доставка
```

Позже тот же принцип пригодится для кода, конфигурации, AI-моделей и снимков
состояния. Первый стрим доказывает только первый переход в этой цепочке.

## Что входит в работу

- открыть файл в бинарном режиме;
- читать его фиксированными блоками, не загружая целиком в память;
- вычислить SHA-256 через OpenSSL EVP;
- представить 32 байта хеша как 64 шестнадцатеричных символа;
- вернуть ошибку Rovelle, если файл нельзя прочитать;
- добавить команду `rovelle hash <file>`;
- вручную сравнить результат с `shasum -a 256`.

Следующий стрим добавит каталог CAS, `blob put`, `blob get`, временный файл и
атомарную публикацию. Эти задачи не нужно успевать в первом выпуске.

## Подготовка до эфира

### 1. Инструменты

На текущей машине уже есть Apple Clang, Make, Git, Homebrew и OpenSSL 3. Перед
эфиром нужно установить отсутствующие CMake и pkg-config:

```sh
brew install cmake pkg-config
```

Затем из корня проекта выполнить:

```sh
cmake -S . -B build
cmake --build build
./build/rovelle --help
./build/rovelle version
```

Это проверка сцены перед выступлением, а не часть сюжета стрима. Если установка
или сборка не работает, проблему лучше узнать до выхода в эфир.

### 2. OBS и рабочий стол

- записать локальный пяти минутный ролик и прослушать голос;
- поставить терминалу и редактору шрифт не меньше 18–20 px;
- показывать редактор и терминал крупно, без всего рабочего стола;
- отключить уведомления и закрыть вкладки с личными данными;
- проверить, что в терминале не выводятся токены, `.env` и история команд;
- держать рядом воду и зарядку;
- открыть этот сценарий на втором экране или телефоне.

Для первого эфира достаточно двух сцен: код с терминалом и короткая заставка.

### 3. Репозиторий

До эфира должны существовать только каркас, `rovelle --help`, `rovelle version`
и этот сценарий. Реализацию хеширования заранее писать не нужно. Полезно
открыть документацию OpenSSL EVP и выписать названия нужных функций, чтобы не
тратить эфир на навигацию по поиску.

## Технический план

Желаемый публичный интерфейс:

```c
rovelle_status_t rovelle_hash_file(
    const char *path,
    char out_hex[65]
);
```

Планируемые файлы:

```text
include/rovelle/hash.h
src/hash.c
cli/main.c
CMakeLists.txt
README.md
```

Последовательность реализации:

1. Объявить `rovelle_hash_file()` и явно записать контракт буфера из 65 байт.
2. Открыть файл через `fopen(path, "rb")`.
3. Создать `EVP_MD_CTX` и выбрать `EVP_sha256()`.
4. Читать файл блоками и передавать каждый блок в `EVP_DigestUpdate()`.
5. Проверить различие между концом файла и ошибкой чтения.
6. Завершить digest и преобразовать каждый байт двумя hex-символами.
7. Освободить ресурсы на всех ветках выхода.
8. Подключить библиотеку OpenSSL в CMake.
9. Разобрать аргументы команды `rovelle hash <file>` в CLI.
10. Обновить справку и README.

В реализации не следует писать SHA-256 самостоятельно. Задача выпуска —
потоковое чтение, границы API и обработка ошибок.

## Сценарий по времени

### 00:00–00:05 — холодное открытие

Можно начать так:

> Я около 13 лет не писал на C и сегодня начинаю Rovelle с пустого каркаса.
> В будущем эта система должна доставлять код и модели для веб-приложений,
> производства и робота-пчеловода. Сегодня цель гораздо меньше: дать файлу
> устойчивый идентификатор и не загрузить весь файл в память.

Сразу показать финальную команду, которую хочется получить:

```sh
rovelle hash README.md
```

### 00:05–00:15 — проблема

На двух файлах с разными именами объяснить три свойства:

1. имя и путь не участвуют в идентификаторе содержимого;
2. изменение одного байта меняет идентификатор;
3. большой файл нельзя считать целиком в память.

Нарисовать короткую цепочку `file -> hash -> blob -> release` и остановиться.
Весь будущий control plane в этой части объяснять не нужно.

### 00:15–00:25 — знакомство с каркасом

Показать `CMakeLists.txt`, библиотеку `rovelle_core`, CLI и тип ошибок. Собрать
проект и вызвать `--help` и `version`.

### 00:25–00:40 — проектирование API

Создать `hash.h`, обсудить размер `65`, владение памятью и ошибочные входы.
Перед кодированием вслух сформулировать ожидаемое поведение функции.

### 00:40–01:10 — реализация

Создать `hash.c`: бинарное открытие, цикл чтения, EVP, перевод результата в
hex и единая очистка ресурсов. После каждого законченного шага собирать проект,
чтобы локализовать ошибки компиляции.

### 01:10–01:25 — CLI

Добавить `rovelle hash <file>`, проверить число аргументов и напечатать понятную
ошибку вместе с именем `rovelle_status_t`.

### 01:25–01:30 — обязательная контрольная точка

К этому моменту команда должна работать хотя бы для одного текстового файла.
Если она работает, основная задача стрима выполнена. Оставшееся время идёт на
проверки и уборку кода.

### 01:30–01:45 — ручная проверка

Проверить:

- один файл командами Rovelle и `shasum -a 256`;
- копию того же файла с другим именем;
- пустой файл;
- бинарный файл;
- отсутствующий файл;
- изменение одного байта.

### 01:45–02:00 — завершение

Показать diff, перечислить принятые решения и открыть следующую задачу:
сохранение blob по хешу без частично опубликованных файлов.

## Как говорить во время работы

Перед каждым изменением отвечать вслух на три вопроса:

1. Какое свойство системы сейчас обеспечивается?
2. Какой отказ возможен на этом шаге?
3. Чем я проверю результат?

Если возникла ошибка, сначала проговорить гипотезу, затем проверить её одной
командой. AI можно использовать открыто после собственной гипотезы как справку
или ревьюера. Это сохраняет на стриме инженерный ход мысли.

## Запасной план

Если OpenSSL или CMake отнимают больше 15 минут, зафиксировать проблему в
README и закончить функцию на уровне чтения блоков и подсчёта байтов. Затем
показать задуманный API, объяснить недостающий вызов EVP и завершить эфир с
конкретным первым шагом для продолжения. Не расширять задачу ради компенсации.

Если код заработал раньше, не начинать CAS. Дополнительное время использовать
для обработки ошибок, проверки большого файла и разбора владения ресурсами.

## Критерии готовности

Стрим успешен, если к его завершению:

- `rovelle hash <file>` печатает 64 символа и перевод строки;
- результат совпадает с `shasum -a 256`;
- текстовый, бинарный и пустой файлы обрабатываются потоково;
- отсутствующий или нечитаемый файл возвращает ненулевой код процесса;
- зрителю понятно, зачем хеш нужен следующему слою Rovelle;
- следующий шаг записан одной задачей, без реализации в этом же эфире.

## После эфира

В течение 15 минут:

1. записать фактический результат и незакрытые вопросы;
2. сохранить команды демонстрации в README;
3. выписать один короткий фрагмент для клипа;
4. назвать следующий стрим: **«Пишем хранилище, где одинаковый файл занимает
   место один раз»**.

## Оценка готовности ведущего

Для исследовательского стрима готовность сейчас примерно **7 из 10**. Сильные
стороны — реальная инженерная задача, спокойное отношение к ошибкам и понятная
долгая цель. Главные риски — давно не использовавшийся C, слишком широкий
замысел и отсутствие привычки завершать выпуск в фиксированной точке.

Первый эфир не должен доказывать способность построить всю платформу. Он должен
показать один законченный инженерный шаг и честный способ принимать решения.
