# RVL-004: опубликовать manifest релиза

## Контекст

Rovelle уже умеет:

```text
файл → SHA-256 → blob put → objects/ab/cdef...
hash → blob get → проверенная копия файла
```

Но один релиз приложения состоит из нескольких файлов. Одного хеша blob
недостаточно, чтобы ответить на вопросы:

- какие файлы входят в релиз;
- по каким логическим путям их восстановить;
- одинаковый ли набор файлов получили разные экземпляры приложения.

В этой задаче manifest свяжет логический путь файла с хешем его содержимого.
Сам manifest тоже будет сохранён как blob. Его SHA-256 станет идентификатором
неизменяемой ревизии.

## Что должно получиться

Новая команда:

```sh
./build/rovelle manifest publish <store> <manifest-file>
```

Она должна:

1. Прочитать manifest.
2. Проверить его формат.
3. Проверить, что каждый указанный blob существует и соответствует своему
   хешу.
4. Сохранить manifest через существующий `rovelle_blob_put()`.
5. Напечатать SHA-256 manifest. Это идентификатор ревизии.

## Формат manifest v1

Manifest является обычным текстовым файлом. Пути в первой версии ограничены
ASCII:

```text
ROVELLE-MANIFEST-V1
<sha256><TAB><logical-path>
<sha256><TAB><logical-path>
```

Пример:

```text
ROVELLE-MANIFEST-V1
2b8f...64-символьный-хеш...	public/style.css
ac31...64-символьный-хеш...	server/index.js
```

Между хешем и путём находится один символ табуляции `\t`. Каждая строка,
включая последнюю, заканчивается `\n`.

Пути должны быть расположены строго по возрастанию через `strcmp()`. Благодаря
этому один и тот же набор файлов имеет одно каноническое представление и один
хеш manifest.

## Ограничения первой версии

Логический путь:

- не пустой;
- относительный, то есть не начинается с `/`;
- не заканчивается `/`;
- не содержит `\\`;
- не содержит пустые сегменты, `.` или `..`;
- состоит из ASCII символов `a-z`, `A-Z`, `0-9`, `/`, `.`, `_`, `-`, `@`,
  `[`, `]`.

Manifest:

- содержит правильный заголовок;
- содержит хотя бы одну запись;
- не содержит пустых строк;
- каждая строка содержит ровно два поля: хеш и путь;
- не содержит повторяющихся путей;
- отсортирован по логическому пути;
- ссылается только на существующие и целые blobs.

В эту задачу не входят JSON, каталоги, права доступа, symlinks, сеть,
активация `current`, удаление старых ревизий и Windows.

## Публичные функции

### 1. Проверка строки SHA-256

Сейчас `is_valid_hash()` находится внутри `src/blob.c`. Manifest нужна та же
проверка. Перенеси её в модуль hash и сделай публичной:

```c
int rovelle_hash_is_valid(const char *hash);
```

Контракт:

- вернуть `1`, если строка содержит ровно 64 символа `0-9` или `a-f`;
- вернуть `0` для `NULL` и любого другого значения.

После переноса и `blob get`, и manifest используют одну реализацию.

### 2. Проверка blob без восстановления файла

В `include/rovelle/blob.h` добавить:

```c
rovelle_status_t rovelle_blob_verify(
    const char *store_path,
    const char hash[ROVELLE_SHA256_HEX_SIZE]
);
```

Функция должна:

1. Проверить аргументы и формат хеша.
2. Собрать путь существующей `format_blob_path()`.
3. Вычислить SHA-256 файла по этому пути через `rovelle_hash_file()`.
4. Вернуть:
   - `ROVELLE_OK`, если хеш совпал;
   - `ROVELLE_NOT_FOUND`, если файла нет;
   - `ROVELLE_CORRUPT`, если файл есть, но хеш отличается;
   - соответствующую ошибку для остальных случаев.

`rovelle_blob_get()` после этого может вызвать `rovelle_blob_verify()` перед
копированием или сохранить текущую проверку временной копии. Для этой задачи
не нужно переписывать рабочий `blob get`.

### 3. Публикация manifest

В новом `include/rovelle/manifest.h` объявить:

```c
rovelle_status_t rovelle_manifest_publish(
    const char *store_path,
    const char *manifest_path,
    char out_revision[ROVELLE_SHA256_HEX_SIZE]
);
```

Память под `out_revision` создаёт вызывающий код. Функция заполняет её только
при успешной публикации.

## Реализация по маленьким шагам

### Шаг 1. Вынести проверку хеша

Перенеси `is_valid_hash()` из `src/blob.c` в `src/hash.c`, назови
`rovelle_hash_is_valid()` и добавь объявление в `hash.h`.

Замени вызов внутри `rovelle_blob_get()`.

Контрольная точка:

```sh
rbuild
```

### Шаг 2. Добавить `rovelle_blob_verify()`

Не копируй blob в новый файл. Нужно только получить путь, вычислить реальный
хеш и сравнить его с ожидаемым.

Контрольная точка:

```sh
rbuild
```

### Шаг 3. Проверить логический путь

В `src/manifest.c` создать приватную функцию:

```c
static int is_valid_logical_path(const char *path);
```

В начале `src/manifest.c` пока можно определить тот же предел пути, который
используется в `blob.c`:

```c
#define ROVELLE_PATH_SIZE 4096
```

Понадобятся заголовки `stdio.h`, `stdlib.h` и `string.h`.

Проверяй путь посегментно. Сегмент находится между двумя `/`. Запрещены пустой
сегмент, `.` и `..`.

Примеры:

```text
server/index.js       valid
public/app.css        valid
/etc/passwd           invalid
../secret             invalid
assets//logo.svg      invalid
assets\\logo.svg      invalid
```

### Шаг 4. Открыть и проверить заголовок

В `rovelle_manifest_publish()`:

1. Проверить три аргумента на `NULL`.
2. Открыть `manifest_path` через `fopen(..., "rb")`.
3. Прочитать первую строку через POSIX `getline()`.
4. Убедиться, что она в точности равна `ROVELLE-MANIFEST-V1\n`.

`getline()` сама выделяет память под строку. После работы её нужно освободить
через `free()`.

### Шаг 5. Разобрать записи

Для каждой следующей строки:

1. Убедиться, что строка заканчивается `\n`.
2. Удалить завершающий `\n`, заменив его на `\0`.
3. Найти табуляцию через `strchr(line, '\t')`.
4. Заменить табуляцию на `\0`.
5. Левая часть строки теперь является `hash`, правая `logical_path`.
6. Проверить обе части.
7. Сравнить путь с предыдущим через `strcmp()`.
8. Вызвать `rovelle_blob_verify(store_path, hash)`.

Храни предыдущий путь в отдельном массиве:

```c
char previous_path[ROVELLE_PATH_SIZE];
```

Копируй текущий путь через `snprintf()` с обычной проверкой переполнения.

### Шаг 6. Опубликовать manifest

Если весь файл прочитан без ошибок и найдена хотя бы одна запись:

```c
return rovelle_blob_put(
    store_path,
    manifest_path,
    out_revision
);
```

Manifest становится ещё одним неизменяемым blob. Отдельный алгоритм хранения
для него не нужен.

### Шаг 7. Добавить CLI

Новая команда принимает пять элементов `argv`:

```text
argv[0] rovelle
argv[1] manifest
argv[2] publish
argv[3] store
argv[4] manifest-file
```

После успеха напечатать `out_revision` и перевод строки. После ошибки:

```text
manifest publish failed: ROVELLE_NOT_FOUND
```

Не забудь добавить команду в `print_help()` и `src/manifest.c` в
`CMakeLists.txt`.

## Очистка ресурсов

Перед возвратом из `rovelle_manifest_publish()` должны быть освобождены:

- `FILE *manifest` через `fclose()`;
- память `line`, выделенная `getline()`, через `free()`.

Используй один блок `cleanup`, как в `blob.c`. Ошибка закрытия файла меняет
`ROVELLE_OK` на `ROVELLE_IO_ERROR`, но не должна скрывать уже найденную более
точную ошибку.

## Критерии готовности

### Успешная публикация

Два существующих blob объединяются в manifest. Команда печатает 64-символьную
ревизию. Повторная публикация того же файла печатает тот же хеш.

### Отсутствующий blob

Если одна запись содержит правильный хеш, которого нет в store, команда
возвращает `ROVELLE_NOT_FOUND`. Сам manifest не публикуется.

### Повреждённый blob

Если содержимое объекта не соответствует адресу, команда возвращает
`ROVELLE_CORRUPT`.

### Неканонический manifest

Неверный заголовок, неправильный хеш, опасный путь, повтор пути и неверная
сортировка возвращают `ROVELLE_INVALID_ARGUMENT`.

## Главный архитектурный вывод

Blob отвечает на вопрос «какие это байты?». Manifest отвечает на вопрос «из
каких байтов состоит эта версия приложения и куда их положить?». Хеш manifest
фиксирует весь набор файлов, поэтому изменение одного файла создаёт новую
ревизию, а неизменившиеся blobs переиспользуются.
