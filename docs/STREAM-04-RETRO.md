## Где технически был прав

### Набор объектов ещё не является релизом

Content-addressed storage отвечает на вопрос «где лежат байты с таким SHA-256». Он не отвечает на вопросы:

- какие объекты входят в релиз;
- по каким путям их разместить;
- какую версию набора активировать.

Manifest действительно может стать описанием такого набора.

### Хэш manifest подходит как идентификатор revision

Одинаковое содержимое manifest получает одинаковый SHA-256. Любое изменение manifest создаёт другой идентификатор. Это хорошая основа для неизменяемых revision.

### Неизменившийся файл можно переиспользовать

Если содержимое файла не изменилось, его SHA-256 остаётся прежним. Новый manifest может ссылаться на уже существующий blob. Повторная отправка не требуется, если blob уже есть на принимающей стороне.

### Проверка `fgetc` соответствует текущей маленькой задаче

На этом этапе требовалось только доказать, что после заголовка существует хотя бы один байт. Для этой узкой проверки `fgetc()` подходит.

### После `fclose` указатель больше не обозначает открытый поток

Обнуление `manifest` после попытки закрытия защищает `cleanup` от повторного `fclose`.

## Где формулировку нужно уточнить

### Сейчас опубликован blob manifest, а не полностью проверенный релиз

Текущая функция проверяет заголовок и один байт содержимого. Она пока не проверяет строки `hash<TAB>path`. Поэтому manifest с мусором после заголовка тоже будет опубликован.

До полноценной revision ещё нужны:

- проверка формата SHA-256;
- проверка разделителя TAB;
- проверка безопасного относительного пути;
- запрет повторяющихся путей;
- проверка существования каждого blob;
- однозначный порядок строк или другое правило канонизации.

### Наличие одного байта не означает наличие одной записи

Один перевод строки или произвольный символ проходит текущую проверку. Это нормально для текущего шага, но нельзя позже описывать её как полную валидацию manifest.

### Между проверкой и `blob_put` файл может измениться

Функция сначала открывает и проверяет файл, закрывает его, а затем `rovelle_blob_put` открывает тот же путь повторно. Другая программа теоретически может изменить файл между этими действиями.

Для эксперимента это приемлемо. В более строгой версии следует проверять и сохранять одни и те же прочитанные байты или после сохранения повторно проверять сохранённый объект.

### «Не нужно доставлять второй файл» требует наличия blob на получателе

Если нужный blob уже находится на поде или в общем кеше, его можно не передавать. При первой доставке на чистый узел файл всё равно потребуется скачать.

### Неизменяемость создаёт протокол, а не один только SHA-256

Хэш позволяет заметить изменение. Для реальной неизменяемости хранилище также не должно перезаписывать существующий объект по тому же адресу, а чтение должно проверять содержимое.

## Ошибки и полезные моменты

### `argc == 7` вместо `argc == 5`

Команда состоит из пяти элементов с учётом имени программы:

```text
rovelle manifest publish <store> <manifest-file>
```

Ошибка хорошо разобрана через явное перечисление `argv[0]` — `argv[4]`.

### Перевёрнутая проверка `strcmp`

`strcmp()` возвращает `0`, когда строки равны. Это типичная ошибка в C и хороший материал для отдельного короткого объяснения.

### Спор вокруг `fgetc`

Сначала обсуждение ушло в будущий парсер, где потеря первого символа действительно была бы проблемой. Затем задача была перечитана, и стало ясно, что на текущем шаге файл после проверки сразу закрывается. Это хороший пример того, зачем возвращаться к условию задачи.

### В help всё ещё не хватает строки `blob get` в разделе Usage

Команда описана в `Commands`, но не перечислена в верхнем блоке `Usage`. Это небольшая незавершённая полировка.

### Как рассказывать разбор `man`

Вместо молчаливого чтения:

1. Назвать вопрос.
2. Найти в документации одну строку, которая отвечает на него.
3. Пересказать её своими словами.
4. Сразу применить к текущему коду.

Пример:

> Мне нужно отличить конец файла от ошибки чтения. `fgetc` в обоих случаях возвращает EOF. Поэтому после EOF вызываю `ferror`: ненулевое значение означает ошибку, ноль означает нормальный конец файла.

## Звук

Измерения микрофонной дорожки:

- интегральная громкость: около `-30.4 LUFS`;
- true peak: около `-3.5 dBFS`;
- диапазон громкости: `11.7 LU`.

Средняя громкость остаётся низкой, при этом отдельные пики уже близки к верхней границе. Простое увеличение Gain может вызвать перегрузку. Нужны компрессор с выходным усилением и limiter.

Ориентир для следующей записи:

- Compressor: threshold около `-20 dB`, ratio `3:1`, output gain `+5…+7 dB`;
- Limiter: `-1.5 dB`;
- обычная речь на индикаторе OBS примерно `-18…-10 dB`.

В Shorts звук нормализован до `-16 LUFS` и очищен от постоянного фонового шума.
