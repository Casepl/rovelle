# FUSE-11: вынести проверку SHA-256 в публичный API

## Зачем это нужно

Сейчас проверка строки SHA-256 спрятана внутри `src/blob.c`:

```c
static int is_valid_hash(...);
```

Она нужна не только команде `blob get`. Manifest тоже должен отличать
корректный адрес объекта от случайной строки из 64 символов.

Если скопировать эту проверку в `manifest.c`, появятся две реализации одного
правила. Со временем они могут начать работать по-разному. Поэтому правило
должно принадлежать модулю `hash` и иметь один публичный контракт.

## Что должно получиться

В публичном API появляется функция:

```c
int rovelle_hash_is_valid(const char *hash);
```

Она возвращает:

```text
1  строка является SHA-256 в каноническом формате Rovelle
0  строка не подходит
```

Канонический формат Rovelle:

- ровно 64 символа до завершающего `\0`;
- разрешены цифры `0-9`;
- разрешены маленькие буквы `a-f`;
- большие буквы и остальные символы запрещены.

После изменения `rovelle_blob_get()` использует новую публичную функцию, а
поведение команды не меняется.

## Граница задачи

Ориентир по времени: 45–60 минут. Если к 60-й минуте CTest ещё не подключён,
остановиться после рабочей функции и успешного `rbuild`. Подключение теста
станет первым шагом следующего эфира, а не поводом растягивать этот.

В эту задачу входят только:

1. Перенос проверки из `blob.c` в модуль `hash`.
2. Публичное объявление функции.
3. Замена старого вызова в `rovelle_blob_get()`.
4. Отдельный исполняемый C-тест.
5. Запуск теста через CTest.

В эту задачу не входят:

- дальнейшая реализация manifest;
- проверка существования blob;
- изменение формата хеша;
- поддержка заглавных `A-F`;
- тестовый фреймворк;
- изменение CLI.

## Файлы

Изменить:

```text
include/rovelle/hash.h
src/hash.c
src/blob.c
CMakeLists.txt
```

Создать:

```text
tests/hash_validation_test.c
```

## Шаг 1. Зафиксировать контракт

В `include/rovelle/hash.h` объявить:

```c
int rovelle_hash_is_valid(const char *hash);
```

Перед написанием реализации своими словами ответить в эфире:

1. Почему размер строки должен быть именно 64, хотя массив для результата
   хеширования имеет размер 65?
2. Почему `NULL` здесь превращается в `0`, а не в `ROVELLE_INVALID_ARGUMENT`?
3. Почему заглавные `A-F` не принимаются?

## Шаг 2. Перенести реализацию

Найти `is_valid_hash()` в `src/blob.c` и перенести её логику в `src/hash.c`.

Новая функция должна:

1. Вернуть `0` для `NULL`.
2. Проверить длину строки.
3. Пройти по 64 символам.
4. Для каждого символа проверить два допустимых диапазона.
5. Вернуть `0` при первом неправильном символе.
6. Вернуть `1`, если вся строка прошла проверку.

Удалить старую приватную функцию из `blob.c` и заменить её вызов на
`rovelle_hash_is_valid()`.

### Первая контрольная точка

```sh
export PATH="$PWD/tools:$PATH"
rbuild
```

Сборка должна пройти, а существующая команда `blob get` должна использовать
общую реализацию.

## Шаг 3. Написать отдельный C-тест

Создать `tests/hash_validation_test.c` с обычной функцией `main()`.

Тест не должен знать внутреннее устройство функции. Он вызывает только
публичный API и завершает процесс:

```text
код 0  все проверки прошли
код 1  хотя бы одна проверка не прошла
```

Минимальная таблица случаев:

| Вход | Ожидается | Зачем |
| --- | ---: | --- |
| 64 символа `0-9a-f` | `1` | обычный корректный хеш |
| `NULL` | `0` | отсутствие строки |
| 63 допустимых символа | `0` | строка слишком короткая |
| 65 допустимых символов | `0` | строка слишком длинная |
| один символ `g` | `0` | символ вне hex |
| одна заглавная `A` | `0` | формат должен быть каноническим |
| пробел или перевод строки | `0` | посторонний символ |

При падении тест должен напечатать, какой случай не прошёл. Не нужно печатать
ничего, если все проверки успешны.

## Шаг 4. Подключить тест к CMake

Внутри существующего блока:

```cmake
if(BUILD_TESTING)
    ...
endif()
```

нужно:

1. Создать исполняемый target из `tests/hash_validation_test.c`.
2. Связать его с `rovelle_core`.
3. Зарегистрировать его через `add_test()`.
4. Включить для тестового target те же строгие предупреждения компилятора,
   что и для основного кода.

Не добавляй проверку в shell-скрипт `cli_help_smoke.sh`: валидатор является C
API, поэтому его проще и точнее проверить из C.

## Финальная проверка

Из корня проекта:

```sh
export PATH="$PWD/tools:$PATH"
rbuild
rtest
```

В выводе должны присутствовать и пройти три разных теста:

```text
cli_help_smoke
cas_smoke
hash_validation
```

Затем проверить старое поведение CLI:

```sh
./build/rovelle blob get /tmp/store bad-hash /tmp/result
```

Ожидаемый результат:

```text
blob get failed: ROVELLE_INVALID_ARGUMENT
```

## Критерии готовности

Задача завершена, если одновременно выполнены все условия:

- в `blob.c` больше нет `is_valid_hash()`;
- `rovelle_hash_is_valid()` объявлена в публичном заголовке;
- `blob get` использует новую функцию;
- тест проверяет положительный случай и все основные причины отказа;
- `rbuild` проходит;
- оба теста проходят через CTest;
- CLI по-прежнему отклоняет неправильный хеш.

## Вероятные ошибки

1. Сравнить длину с `ROVELLE_SHA256_HEX_SIZE`, то есть с 65. В длину C-строки
   завершающий `\0` не входит, поэтому сравнивать нужно с 64.
2. Вернуть `ROVELLE_INVALID_ARGUMENT` из функции типа `int`. Ненулевое значение
   будет воспринято вызывающим кодом как «хеш корректный».
3. Оставить старую приватную реализацию в `blob.c`. Тогда единый источник
   правила фактически не появится.

## Решение, которое нужно принять на стриме

Как тест будет сообщать о конкретном падении без тестового фреймворка:

- отдельная проверка с понятным сообщением для каждого случая;
- небольшая таблица входов и ожидаемых результатов с циклом.

Оба варианта допустимы. Выбери тот, который сможешь объяснить зрителю.

## Первый шаг на стриме

Открой рядом три файла:

```text
src/blob.c
src/hash.c
include/rovelle/hash.h
```

Найди `is_valid_hash()` и сначала вслух сформулируй её контракт. После этого
перенеси только объявление и реализацию. До тестов и CMake пока не переходи.

## Хук для начала стрима

> Вот строка из 64 символов. Внутри одна `g`. Длина правильная, но это уже не
> SHA-256. Сегодня вынесу проверку в общий API и впервые подключу CTest.

Сразу после этой фразы показать рядом корректную строку и такую же строку с
одной `g`. Не начинать с истории проекта или определения SHA-256.

## Кандидаты для Shorts

### Основной: первый C-тест без фреймворка

Записать отдельный короткий дубль после подключения теста:

> Чтобы проверить C-функцию, мне не нужен тестовый фреймворк. Это обычная
> программа с `main()`: ноль означает, что проверки прошли, другой код означает
> ошибку. CTest запускает её и показывает результат вместе с остальными тестами.

На экране показать только `main()`, регистрацию `add_test()` и успешный запуск
`ctest`. Целевая длина: 20–30 секунд.

### Запасной: ошибка становится `true`

Использовать, только если этот вопрос действительно возникнет во время работы:

> В C код ошибки легко принять за `true`. Если булева функция вернёт
> `ROVELLE_INVALID_ARGUMENT`, это ненулевое число. Вызывающий код решит, что хеш
> корректный. Поэтому такой валидатор возвращает только `0` или `1`.

Не разыгрывать ошибку специально. Нужен настоящий момент из стрима или
отдельное честное объяснение после него.
