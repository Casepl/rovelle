# Стрим 6: manifest не публикует неправильную revision

## Связь с предыдущим стримом

На пятом стриме проверка текстового SHA-256 была вынесена из `blob.c` в общий
API:

```c
int rovelle_hash_is_valid(const char *hash);
```

`blob get` уже использует эту функцию. Сегодня появляется второй потребитель:
разбор строк manifest.

```text
Стрим 4: manifest проверяет заголовок и сохраняется как revision
Стрим 5: общее правило проверки SHA-256
Стрим 6: каждая запись manifest проходит это правило до публикации
```

## Результат эфира

Команда:

```text
rovelle manifest publish <store> <manifest-file>
```

должна читать все записи после заголовка:

```text
ROVELLE-MANIFEST-V1
<hash><TAB>public/style.css
<hash><TAB>server/index.js
```

и вызывать `rovelle_blob_put()` только после успешной проверки всего файла.

Manifest отклоняется с `ROVELLE_INVALID_ARGUMENT`, если:

- после заголовка нет ни одной записи;
- в строке нет `TAB`;
- часть до `TAB` не проходит `rovelle_hash_is_valid()`;
- после `TAB` нет пути;
- запись не заканчивается переводом строки или содержит данные после него.

Главный наблюдаемый результат:

```text
ошибка в одной записи -> manifest не сохраняется -> revision не появляется
```

## Граница задачи

Сегодня нужно:

1. заменить одиночный `fgetc()` на чтение записей через `fgets()`;
2. разделить строку по первому `\t`;
3. проверить hash через готовую `rovelle_hash_is_valid()`;
4. проверить непустой путь и окончание строки;
5. убедиться, что есть хотя бы одна запись;
6. сохранить manifest только после успешного прохода;
7. показать корректный и ошибочный сценарии.

Сегодня не нужно:

- проверять существование указанных blobs;
- добавлять `rovelle_blob_verify()`;
- запрещать `..` и абсолютные пути;
- проверять сортировку и дубликаты путей;
- добавлять `refs/current`;
- менять CLI или формат CAS.

Эти ограничения нужно назвать в начале. Иначе задача незаметно превратится в
полный парсер и снова выйдет за границу одного эфира.

## Заход

Сначала показать существующее поведение на одном неправильном manifest:

```text

```

Если текущая команда печатает revision, конфликт задачи виден без длинного
объяснения.

После демонстрации открыть:

```text

```

Связь с прошлым результатом:

> В прошлый раз я сделал единое правило для строк SHA-256. Сейчас не копирую
> его в manifest, а вызываю готовый `rovelle_hash_is_valid()`.

## План эфира

### 00:00–00:07. Показать дефект

1. Собрать manifest с правильным заголовком и неправильным hash.
2. Запустить `manifest publish`.
3. Показать, что текущая версия создаёт revision.
4. Сформулировать ожидаемое поведение: команда должна завершиться ошибкой до
   `rovelle_blob_put()`.

Вопрос блока:

```text
что сейчас проходит незамеченным
```

### 00:07–00:20. Прочитать одну запись

1. Завести буфер строки.
2. Читать строки после заголовка через `fgets()`.
3. Найти первый `\t` через `strchr()`.
4. При отсутствии разделителя вернуть `ROVELLE_INVALID_ARGUMENT`.
5. Временно заменить `\t` на `\0`, чтобы hash стал отдельной C-строкой.

Опоры речи:

```text
в буфере одна запись
TAB делит два поля
временный ноль завершает hash
```

### 00:20–00:35. Использовать результат прошлого стрима

1. Передать часть до `TAB` в `rovelle_hash_is_valid()`.
2. Ошибочный hash отклонить.
3. Проверить, что путь после `TAB` не пуст.
4. Проверить завершающий `\n` и отсутствие символов после него.
5. Посчитать успешные записи.

Главный вопрос:

```text
доказала ли строка оба обязательных поля
```

### 00:35–00:47. Не публиковать частичный результат

1. После цикла проверить `ferror(manifest)`.
2. Отклонить manifest с нулём записей.
3. Закрыть файл.
4. Только теперь вызвать `rovelle_blob_put()`.

Ключевой инвариант:

```text
сначала проверен весь документ -> потом появляется revision
```

### 00:47–01:00. Доказательство результата

Проверить отдельно:

1. корректную запись;
2. hash с одной `g`;
3. строку без `TAB`;
4. пустой путь.

До и после ошибочной публикации посчитать объекты:

```sh
find tmp/rovelle-demo/store/objects -type f | wc -l
```

Число объектов после ошибочного manifest не должно увеличиться.

Остановиться после этого результата. Не начинать проверку существования blobs.

## Концовка

Смысл финала:

```text
раньше -> что изменилось -> доказательство -> следующий риск
```

Возможная формулировка:

> Раньше любого текста после заголовка было достаточно, чтобы получить
> revision. Теперь Rovelle разбирает каждую запись и использует валидатор с
> прошлого стрима. Hash с `g`, отсутствующий `TAB` и пустой путь останавливают
> публикацию, поэтому новый объект не появляется. Следующий вопрос — существует
> ли blob, на который ссылается уже правильно записанный hash.

Не читать эту формулировку дословно. Опоры:

```text
мусор раньше проходил
три причины отказа
объект не появился
дальше существование blob
```

## Материал для Shorts

Лучший сюжет не требует контекста всего проекта:

```text
manifest с неправильным hash получает revision
       ↓
добавляется разбор hash<TAB>path
       ↓
один символ меняется на g
       ↓
публикация отклонена, число объектов не изменилось
```

Возможный отдельный заход для озвучки:

> Эта строка выглядит как SHA-256: в ней 64 символа. Но одной буквы `g`
> достаточно, чтобы адрес перестал быть hex. Если она находится внутри
> manifest, весь релиз нужно отклонить до публикации.

Целевая длина: 25–40 секунд. Терминал должен показывать левую часть команды и
сообщение `ROVELLE_INVALID_ARGUMENT`.
