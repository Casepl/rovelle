# Стрим 7: релиз ссылается на файл, которого нет

Подробная карточка для работы на эфире:

## Откуда продолжаем

На шестом стриме `rovelle_manifest_publish()` научилась разбирать записи
`hash<TAB>path`: проверять hash общим валидатором, непустой путь, наличие
перевода строки и хотя бы одной записи. Сохранение manifest выполняется после
прохода по документу.

При подготовке 24 октября 2026 года текущий код собран через `./tools/rbuild`.
Все три существующих теста прошли через `./tools/rtest`.
Отдельный эксперимент на временном store показал:

| Вход | Текущее поведение |
|---|---|
| Hash из `g` | `ROVELLE_INVALID_ARGUMENT` |
| Корректный hash отсутствующего объекта | Публикация успешна |
| Hash существующего исправного объекта | Публикация успешна |
| Тот же hash после порчи объекта | Публикация успешна |

Это проверка текущего рабочего дерева, включая изменения шестого стрима,
которые ещё не закоммичены. Это не ретроспектива видеозаписи.

## Задача на 60–90 минут

Перед публикацией manifest проверить наличие и целостность каждого указанного
blob. Если хотя бы один объект недоступен или его содержимое не соответствует
hash, публикация завершается ошибкой до сохранения manifest.

Наблюдаемый результат: список файлов с правильными адресами больше не считается
достаточным основанием для публикации — сами файлы тоже проходят проверку.

Предлагаемый небольшой API модуля blob:

```c
rovelle_status_t rovelle_blob_verify(
    const char *store_path,
    const char hash[ROVELLE_SHA256_HEX_SIZE]
);
```

Контракт для этого эфира:

| Условие | Статус |
|---|---|
| Некорректные аргументы | `ROVELLE_INVALID_ARGUMENT` |
| Объект отсутствует | `ROVELLE_NOT_FOUND` |
| Ошибка чтения | `ROVELLE_IO_ERROR` |
| Содержимое не соответствует адресу | `ROVELLE_CORRUPT` |
| Hash содержимого совпадает с адресом | `ROVELLE_OK` |

Проверка ничего не восстанавливает и не создаёт выходной файл. Ошибка проверки
передаётся из manifest вызывающему коду. Существующий `blob get` сохраняет свой
контракт; его рефакторинг не входит в обязательный результат.

Учесть при реализации: текущая `rovelle_hash_file()` считает любую ошибку
открытия файла `ROVELLE_NOT_FOUND`. Для указанного контракта потребуется
небольшое исправление: различать `ENOENT` и остальные ошибки открытия.
Подробнее — в карточке для джуна.

## Что открыть

- `src/manifest.c`: цикл записей и точку вызова `rovelle_blob_put()`.
- `src/blob.c`: `format_blob_path()` и проверки в `rovelle_blob_get()`.
- `include/rovelle/blob.h`: публичную границу модуля.
- `include/rovelle/hash.h` и `src/hash.c`: контракт `rovelle_hash_file()`.
- `tests/cas_smoke.sh` и `CMakeLists.txt`: образец интеграционной проверки.

## Первый шаг — до десяти минут

Создать отдельный временный store и один исходный файл. Сохранить файл через
`blob put`, записать полученный hash в manifest и показать успешную публикацию.
Затем заменить hash на 64 нуля и повторить публикацию. Убедиться, что такого
объекта в этом store нет. Зафиксировать наблюдение: команда сейчас принимает
ссылку на отсутствующий файл.

Перед правкой сформулировать своими словами: какая проверка шестого стрима
уже работает и чего она ещё не доказывает?

## Контрольные точки

1. Воспроизведён дефект, назван ожидаемый статус.
2. Проверка одного blob различает исправный, отсутствующий и повреждённый
   объект. Решение о её устройстве принимает владелец.
3. Manifest использует проверку для каждой синтаксически корректной записи;
   любая ошибка останавливает публикацию.
4. Автоматическая интеграционная проверка подтверждает поведение CLI и
   отсутствие нового объекта manifest при отказе.

Если времени мало, остановиться после проверенного API одного blob и явно
оставить подключение к manifest следующему эфиру.

## Проверки готовности

Сборка и регрессии:

```sh
./tools/rbuild
./tools/rtest
```

Добавить отдельный тест manifest в CTest. Матрица входов для него:

| Сценарий | Ожидание |
|---|---|
| Все blobs существуют и исправны | Успех, revision напечатана |
| Корректный hash отсутствующего blob | Ошибка `ROVELLE_NOT_FOUND` |
| Объект по правильному адресу испорчен | Ошибка `ROVELLE_CORRUPT` |
| Первая запись исправна, вторая ссылается на отсутствующий blob | Отказ всего manifest |
| Некорректный hash | Сохраняется `ROVELLE_INVALID_ARGUMENT` |

Для каждого отрицательного сценария использовать manifest, который ранее не
публиковался. Сравнивать число файлов в `store/objects` непосредственно до и
после попытки публикации: число не должно расти. Сам store заранее создать
через успешный `blob put`. Проверять код завершения и конкретный статус;
одного текста сообщения недостаточно.

Для порчи объекта использовать только отдельный временный store:
`objects/<первые 2 символа hash>/<остальные 62>`. Проверить, что испорчен именно
blob данных, а не ранее опубликованный manifest.

## Ловушки и границы

- `rovelle_hash_is_valid()` проверяет запись адреса; наличие файла и совпадение
  содержимого — отдельные условия. Проверки только существования недостаточно.
- Повторная публикация уже существующего manifest не увеличивает число
  объектов даже при ошибочной реализации. Поэтому отрицательному сценарию
  нужен новый manifest и проверка статуса команды.
- Между проверкой и последующим чтением файл может измениться. Этот срез не
  обеспечивает транзакцию или защиту от параллельной порчи store. Не обещать
  зрителю гарантированно разворачиваемый релиз только на основании этой проверки.

Без расширения задачи на `refs/current`, развёртывание файлов, сортировку,
дубликаты, безопасность путей или полный бинарно-устойчивый парсер manifest.
Найденные проблемы парсера записать отдельно.

## Одно решение владельца

Где должна жить проверка содержимого объекта: в manifest или за публичной
функцией модуля blob? Предложение — отдельный API blob, потому что раскладка
CAS уже принадлежит этому модулю. До реализации объяснить, какую зависимость
это позволяет не переносить в manifest.
